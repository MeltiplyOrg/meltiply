# Frontend capability inventory

This document records the current creator-facing interface. Backend endpoints and reference-design examples do not imply a shipped screen. Use [UI ownership](frontend-ui.md) and [layout](frontend-layout.md) for implementation; [`COMMUNITY_LIMITS`](../packages/domain/src/index.ts) leaves community resource allowances unrestricted while retaining quota machinery for hosted policies.

## Collection behavior

- Table, Calendar, and Grid share Post identity and real publishing state. Table grouping/columns change presentation; Calendar uses real dates and explicit scheduling entry. There is no drag-rescheduling contract.
- Posts Table includes Likes, Cmts, Shrs, Saves, Clicks, Views, Impr., and Reach in the Columns menu. Published Channel snapshots are summed once per Post using each Channel's latest stored measurement; measured zeros stay zero. Drafts, unpublished Posts, absent snapshots, and untracked metrics show `-`. Saves and Clicks are currently untracked. The dedicated Analytics page reads the same stored snapshots for a published cohort; there is no cross-platform audience deduplication.
- Grid cards show the four essential counters (views, likes, comments, shares) in a separate, single-line footer with leading icons and compact localized values. They reuse the Post's stored analytics without per-card requests; exact values and metric names remain available to assistive technology.
- Posts initially reads at most 60 records. Grid shows up to 60 matching cards with bottom Previous/Next page navigation; Table appends the next 60 through Load more. Loaded pages are cached in workspace-scoped browser memory for view/route reuse, not persistent storage. Filters apply to loaded records and reset the Grid page; selections survive page navigation. Calendar retains its month event query.
- Profile selection lives in collection filters or jump search, not sidebar sections. All Brand Profiles is aggregate review. Composition can select several profiles, saving one independently owned Post and separate media copies per profile; this does not give a Post multiple owners.
- Facebook connection lists directly managed Pages and, with `business_management` consent, Pages assigned through Business Manager. Every discovery edge is paginated and duplicate Page IDs appear only once. Existing grants must reconnect to add business discovery permission; the current assignment ticket is a snapshot and cannot gain that permission.
- Posts Platform, Brand Profile, and status filters use multi-select checklists: empty means all, values within a field match with OR, and separate fields combine with AND. One selected profile scopes composition; multiple profiles remain aggregate review. Top-bar jump search covers pages and loaded profiles; route search covers the current collection, not a global index.
- Composer Destinations uses an explicit multi-profile checklist and provider-grouped accounts labelled by owner. Drafts need no channels; scheduling/publishing needs a channel per selected profile. Per-profile progress retains successful copies after failures, repeated saves update their identities, and retrying an unchanged partially queued composition does not resubmit completed profiles.
- Composer ownership guidance, validation, and per-profile progress use workspace profile names with localized fallbacks when a profile is unavailable.
- Selection belongs to loaded authorized records and survives view/filter/group presentation changes. Select-all is visually checked only for the whole visible set. The shared pill reports the real count; confirmed batches remove successes and retain failures.
- Post inspection uses the canonical edge/phone drawer and real properties, caption, attachments, Queue membership/assigned time, and Channel outcomes. Composing and editing open the same drawer, whose footer pins the save state and one action resolved by Draft, Queue, Schedule, or Now. Queue mode requires one owning Brand Profile and assigns a future slot without manual date/time input; manual modes retain multi-profile composition. Deleting a stored Post or disconnecting a Channel does not remove published platform copies.
- Successful Post deletion removes the composition from Table, Calendar, and Grid, including after switching views or reloading. Retained Distribution history does not put deleted Posts back into Calendar.
- Queue configuration changes affect new allocations only. Removal releases a safely unclaimed reservation without shifting others; Provider-owned work must settle. Retirement rejects unresolved Posts and retains historical membership. See [publishing semantics](../frontend/public/content/docs/publishing.mdx#weekly-queues).
- One animation implementation is retained. There is no separate motion mode, preference provider, root flag, or alternate-mode branch.

## Public surfaces

The landing page explains supported publishing workflows using clearly labeled local sample content; that sample cannot publish or persist authenticated workspace Posts. Public guides cover setup, ownership, Channels, composition/media, publishing, Settings, recovery, resource responsibility, and legal/storage policy.

Public article search uses its build-time documentation index and a canonical shared trigger/dialog. It is separate from app jump search. Landing, docs, and app share palette/fonts, while keeping their own product-explanation, reading, and operating layouts.

## Not shipped in the interface

| Capability                               | Current boundary                                                                                                                                                                               |
| ---------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Workspace switching                      | Identity is read-only; the active session resolves the workspace.                                                                                                                              |
| Inbox/replies                            | No in-app comment reader or reply workflow; use the native platform. Backend syncing does not create an app route.                                                                             |
| AI Studio/Plugs                          | No simulated assistant, recommendation, integration directory, or automation configuration screen.                                                                                             |
| Team/admin/billing                       | No checkout, portal, payment integration, or notification configuration. Membership invites, roles, installation lifecycle, and the audit trail live only in Settings' Administration surface. |
| Standalone media library                 | Uploads and attachment selection belong to a Post composition.                                                                                                                                 |
| Profile restore                          | No deleted-profile browser or restore control. App deletion permanently removes owned records; retained backend soft-delete operations do not undo it.                                         |
| Identity editing/custom appearance modes | Account identity is read-only; there are no custom accent, density, layout-mode, or motion-mode settings.                                                                                      |

Adding a capability requires an explicitly approved, authorized end-to-end workflow with real data, meaningful pending/error/empty states, scope isolation, updated guides, and actual-surface verification. Do not restore a demo control merely because its API or reference markup exists.
