# UI translations

The frontend app ships English, Spanish, Brazilian Portuguese, French, German,
Italian, Simplified Chinese, and Vietnamese. English source copy is the
translation key: `t("Dashboard")` stays `t("Dashboard")`, and a missing target
value falls back to the English string. Catalogs live as data under
[`frontend/app/src/locales`](../frontend/app/src/locales):

```
locales/
  glossary.json        shared product vocabulary and intentionally identical strings
  en/ui.json           every English UI string mapped to itself
  en/status.json       status identifiers mapped to English labels
  <code>/ui.json       target UI strings (es, pt-BR, fr, de, it, zh, vi)
  <code>/status.json   target status labels
```

`translate()` and `tStatus()` read the target catalogs through the
`uiTranslations` and `statusTranslations` maps, so the runtime and the
translation pipeline share one source of truth. Dev-only pseudo-localization
still applies after lookup.

## Adding or changing English copy

1. Call `t("New English string")` as usual.
2. The catalog test fails until `en/ui.json` contains the literal. Add the key
   with the English string as its value (status labels go in `en/status.json`).
3. Draft the target language offline:

   ```bash
   bun run i18n:generate --target es --dry-run   # list the strings that would be sent
   bun run i18n:generate --target es
   ```

4. Review the `es/ui.json` or `es/status.json` diff. Generation writes nothing
   until every namespace succeeds, and any dropped or renamed placeholder aborts
   the run with the committed files byte-identical.
5. Run `bun run i18n:check` (or the app check, which includes it).

Only keys missing from the target are sent. The committed target file is the
cache, so unchanged strings cost nothing; an edited English string is a new key
and is translated once. Generation never runs in CI.

## Commands

| Command                                               | Purpose                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------ |
| `bun run i18n:check`                                  | Deterministic, model-free catalog gate. Used by the frontend app check and CI. |
| `bun run i18n:generate --target es --dry-run`         | Show the pending keys without calling the provider or writing files.           |
| `bun run i18n:generate --target es`                   | Draft missing values for the target locale and write its files.                |
| `bun run i18n:generate --target es --provider ollama` | Draft locally with no account or key.                                          |
| `bun run i18n:generate --target es --force`           | Retranslate every existing value. Use only for a reviewed terminology change.  |
| `bun run i18n:generate --target es --model <model>`   | Override the active backend's model.                                           |
| `bun run i18n:lock -- --keys 'legal.*'`               | Lock reviewed translations. Commit `.shipi18n/locks.json`.                     |

`i18n:check` runs Shipi18n with the explicit `brace` placeholder grammar,
`--fail-on error`, full coverage, and the structural rules the product needs
(untranslated values, invented placeholders, missing or collapsed plural forms)
escalated to errors. Its ignore-key list comes from `glossary.json`, so
intentionally identical values (Platform names, identifiers, examples) do not
false-positive. The check makes no network request and needs no credential.

## Providers and credentials

Generation supports two backends behind the same `TranslationProvider` seam:

- **Workers AI** — used when both Cloudflare credentials are present. The free
  daily allowance covers normal catalog work, and the fallback model handles a
  primary outage or malformed output.
- **Ollama** — local, free, no account, key, or network egress. Used
  automatically when Workers AI credentials are absent, or force it with
  `--provider ollama`.

`I18N_PROVIDER=auto` (default) selects Workers AI when both credentials exist
and Ollama otherwise. `workers-ai` requires credentials; `ollama` always stays
local. There is no credential-free hosted provider — “no credentials” means
local inference.

### Credential-free local generation (Ollama)

Install [Ollama](https://ollama.com/download), run `ollama serve`, and pull a model
(`ollama pull qwen3:8b`, about 5 GB). Then:

```bash
bun run i18n:generate --target es --provider ollama
```

With no `WORKERS_AI_*` values, `--provider` is optional because `auto` selects Ollama.

Everything stays on the machine. CPU-only inference works but is slower; a GPU
helps. Override the endpoint with `I18N_OLLAMA_URL` and the model with
`I18N_OLLAMA_MODEL` or `--model`. If the server is down or the model is missing,
generation prints the exact `ollama serve` / `ollama pull` command and writes
nothing.

### Workers AI credentials

Create a Workers AI API token (Read + Edit, account-scoped) and copy the Account ID
from the same page; `bunx wrangler whoami` also prints it. The token cannot deploy
Workers or other infrastructure. Put both in the ignored root `.env`, never in source
or logs. Generation reads `process.env`; export `.env` first if direnv is not loading it:

```bash
set -a; . ./.env; set +a
```

Generation reads [`.env.example`](../.env.example) values from the environment:

| Variable                | Default                         | Purpose                                                          |
| ----------------------- | ------------------------------- | ---------------------------------------------------------------- |
| `I18N_PROVIDER`         | `auto`                          | `auto`, `workers-ai`, or `ollama`.                               |
| `WORKERS_AI_ACCOUNT_ID` | unset                           | Cloudflare account identifier; required for `workers-ai`.        |
| `WORKERS_AI_API_TOKEN`  | unset                           | Workers AI-scoped token (Read + Edit). Never commit or log it.   |
| `I18N_MODEL`            | `@cf/zai-org/glm-4.7-flash`     | Primary Workers AI model.                                        |
| `I18N_FALLBACK_MODEL`   | `@cf/google/gemma-4-26b-a4b-it` | Workers AI fallback for outages or malformed JSON.               |
| `I18N_OLLAMA_URL`       | `http://127.0.0.1:11434`        | Local Ollama base URL.                                           |
| `I18N_OLLAMA_MODEL`     | `qwen3:8b`                      | Locally pulled model.                                            |
| `I18N_SEED`             | `20261019`                      | Fixed sampling seed; override to reproduce a batch or reroll it. |
| `I18N_TIMEOUT_MS`       | `120000`                        | Per-request timeout.                                             |

Generation uses `temperature: 0`, a bounded `max_tokens`, and bounded
exponential backoff for rate limits, timeouts, and 5xx responses. Workers AI
fails immediately on authentication, permission, or quota errors. Seeding is
best effort: changing the model, prompt, glossary, or provider can change output
even with the same seed. The committed locale file plus the model-free check is
what makes CI deterministic.

### Default model choice

The defaults in the variable table above are the reviewed choice. Rationale, not a
leaderboard: reasoning must be disabled because models otherwise spend more output
tokens thinking than translating; the catalog (about 1,130 strings) costs roughly
1,000 neurons, well inside the 10,000-neuron daily allowance, so retries and reasoning
dominate cost rather than per-token price. The fallback model covers a primary outage
or malformed JSON. Do not add a model to the defaults without measuring it against the
real catalog and checking it returns valid JSON with placeholders intact.

## Glossary, locks, and review

[`locales/glossary.json`](../frontend/app/src/locales/glossary.json) holds:

- `style`: per-language tone guidance and variant/register choice.
- `keepVerbatim`: product names, Platform names, identifiers, and examples that
  must survive verbatim. These also become the check's ignore keys and the
  catalog test's allowlist.
- `preferredTranslations`: the product's domain vocabulary (Brand Profile,
  Post, Channel, Workspace) used verbatim in the generation prompt.
- `intentionallyIdentical`: additional strings that stay identical (shortcuts
  and single-letter labels).

Review the generated diff before committing. After review, lock the approved
translations with `bun run i18n:lock`; `.shipi18n/locks.json` stores hashes, not
strings, and lets the check warn when a later edit replaces reviewed wording.
Normal generation only fills missing keys; `--force` is the only path that
replaces existing values and always needs a reviewed diff.

## Adding a language

1. Add the locale code and label to `supportedLanguages` in
   [`i18n.tsx`](../frontend/app/src/lib/i18n.tsx).
2. Import its `ui.json` and `status.json`, then add both to the
   `uiTranslations` and `statusTranslations` maps.
3. Create `locales/<code>/ui.json` and `locales/<code>/status.json` (empty
   objects are fine). Add `style.<code>` and
   `preferredTranslations.*.<code>` to the glossary. Decide the variant and
   register explicitly: the current set uses `pt-BR`, French `vous`, German
   `Sie`, Italian `tu`, Simplified Chinese `zh`, and Vietnamese `bạn`.
4. Run `bun run i18n:generate --target <code>`, review the diff, then
   `bun run i18n:check`.
5. Lock the reviewed catalog with
   `bun run i18n:lock -- --lang <code>`.
6. Add the new locale to the runtime tests (`supportedLanguages` loop and
   status label test).

`i18n:check` discovers the new locale directory automatically. RTL locales such
as Arabic need layout work (logical CSS properties and direction) before they
can ship; Slavic plural categories need ICU plural support, which is out of
scope for the current flat `{count}` strings.
